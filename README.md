# Hot Streak Habits

A small local-first habit tracker. No build step, no backend, no login —
open `index.html` and it works.

## Running it

Just double-click `index.html` (or open it in a browser directly). Everything
runs client-side; your habits are saved in the browser's `localStorage`, tied
to this specific file's location. There's nothing to install and nothing to
start — no `npm install`, no dev server.

To actually use it as a phone app with reminders (see "Reminders" below), you
need to host these files somewhere over HTTPS and open that URL on your
phone — opening the raw file doesn't support installing to your home screen
or notifications on mobile. Any static host works (GitHub Pages, Netlify,
Vercel, etc.) since there's still no server-side code involved, just files.

If you later want a real dev workflow (hot reload, etc.), you can drop this
into a Vite + React project — see "Growing beyond one file" below.

## File structure

```
index.html      <- page shell, loads React/Babel from a CDN, links styles.css,
                    and contains the entire app as one inline <script type="text/babel">
styles.css      <- all visual styling, theming (light/dark), and animations
manifest.json   <- PWA metadata (name, icons, colors) so phones can install it
sw.js           <- service worker: caches the app shell for offline use, and
                    is required by iOS before notifications will work at all
icon-192.png    <- app icon (small)
icon-512.png    <- app icon (large / maskable)
privacy.html    <- standalone privacy policy page, required by both app
                    stores at submission; not linked from the app itself

www/            <- a COPY of the six files above, kept in sync via
                    `npm run sync` — see "Native app wrapping" below
android/        <- native Android project (generated by Capacitor, not
                    hand-edited)
ios/            <- native iOS project (generated by Capacitor, not
                    hand-edited)
capacitor.config.json, package.json, sync-www.js
                <- Capacitor/npm plumbing for the native wrap
```

`index.html` and `styles.css` are the only files with real logic in them —
the rest are PWA plumbing (icons, manifest, service worker) needed for phone
install and notifications. Why one script instead of splitting into
`components/HabitCard.js`, `utils/streaks.js`, etc. like a typical React
project? Because there's no build tool here (no Vite/webpack). The in-browser
Babel transformer that turns the JSX into real JavaScript can only do that
for a `<script>` that's already inline in the HTML — it can't safely fetch a
*separate* local `.js` file when the page is opened as a bare `file://` URL
(the browser blocks that fetch for local files). Keeping it inline is what
lets you double-click the file and have it just work.

Inside that one script, `index.html` is organized top to bottom in the order
things depend on each other:

1. **Date helpers** — turn a JS `Date` into a `"YYYY-MM-DD"` string key
2. **Streak math** — pure functions that compute streaks from a list of dates
3. **localStorage helpers** — load/save the habit list, load the theme
4. **Small components** — `EmptyState`, `WeekDots`, `Confetti`
5. **`HabitCard`** — one habit's row: emoji, streak, week dots, edit/delete
6. **`AddEditModal`** — the bottom-sheet form for creating/editing a habit
6b. **`ThemeModal`** — the cosmetic theme shop (see "Cosmetic theme packs" below)
7. **`App`** — top-level state (the habit list, theme, which modal is open)

## The data model

Each habit is a plain object:

```js
{
  id: "1785268515092-qf7dyr",
  name: "Eat chicken",
  emoji: "🍎",
  intervalDays: 2,                    // the "plan": check in at least every 2 days
  completedDates: ["2026-07-27", "2026-07-25"], // any order
  createdAt: "2026-07-25",
  reason: "More protein, more energy, feel stronger.", // optional, shown again after a failure
  lastAcknowledgedFailure: "2026-07-27",   // which missed due date you've already reflected on
  remindersEnabled: false,            // per-habit buzzer mute (default true/undefined = on)
}
```

`intervalDays` is what makes a habit "every day" (`1`, the default) vs.
"every 2 days," "weekly," etc. Everything else about the habit — its streak,
whether it's due, how its week dots render — is derived from this one number
plus `completedDates`.

`completedDates` is the *only* source of truth. There's no stored
`currentStreak` or `longestStreak` field — both are calculated fresh from
`completedDates` every time they're needed. That's deliberate: if you stored
the streak as its own number, it would be possible for it to drift out of
sync with the actual dates (e.g. after editing history, fixing a bug, or a
partial save). Deriving it every render means the number on screen can never
lie about what's actually in `completedDates`.

## How the streak calculation works

This is the trickiest part of the app, so it's worth walking through.

### Why not just use `Date.toISOString()`?

`toISOString()` converts a date to UTC first. If you check off a habit at
9pm and you're west of Greenwich (e.g. US timezones), UTC has already rolled
over to tomorrow — so the habit would silently get logged under the wrong
day. `toDateKey()` instead builds the `"YYYY-MM-DD"` string manually from
`date.getFullYear()`, `getMonth()`, `getDate()`, which all read the date in
the *browser's local timezone*. That keeps "today" anchored to the user's
actual calendar day.

### Plans: `intervalDays`

The original version of this app assumed every habit was daily. Now each
habit has a "plan" — `intervalDays` — which is just how many days apart
check-ins are allowed to be. `1` means every day; `2` means every other day;
`7` means weekly. This is what makes something like "eat chicken every
second day" work: check in Monday, skip Tuesday freely, and Wednesday is
the day you're on the hook again.

It's picked with a slider in the add/edit sheet, capped at 1–7 days (daily
through weekly) rather than free-typed, since that's the realistic range
for a habit you check in on by hand. `intervalLabel(days)` turns the raw
number into words ("Daily", "Weekly", "Every 3 days").

### Current streak: `getCurrentStreak(completedDates, intervalDays)`

The obvious approach — "count consecutive days ending today" — has a UX
problem: the instant midnight passes and you haven't checked in yet, your
streak would show `0`, even though you technically still have the rest of
today to save it. That kills the "don't lose your streak" tension the app is
built around.

So instead of asking "was every single day filled in," the function asks
"has too much time passed since the last check-in":

- Find the most recent completed date.
- If more than `intervalDays` have passed since then with nothing logged,
  the due date has already come and gone — the streak is broken, return `0`.
  (For a daily habit that's "more than 1 day," i.e. yesterday wasn't done
  either — the same rule as before, just generalized.)
- Otherwise, walk backwards through the check-in history counting how many
  in a row are each within `intervalDays` of the next one. A bigger gap
  anywhere in the history means a due date was missed at that point, which
  is where the run started.

Worked example for "every 2 days," last check-in Monday:
- **Tuesday**: 1 day since Monday, ≤ 2 → still alive, free skip day.
- **Wednesday**: 2 days since Monday, ≤ 2 → still alive, but this is the due
  date — there's time left today, not tomorrow.
- **Thursday**: 3 days since Monday, > 2 → the streak already broke, because
  Wednesday passed with nothing logged.

### Longest streak: `getLongestStreak(completedDates, intervalDays)`

Same "gap ≤ intervalDays" rule as the current streak, just scanning the
*entire* history instead of stopping at the first break: walk through the
sorted dates comparing each one to the previous. If the gap is within the
plan's interval, the run continues; otherwise a new run starts. The longest
run seen along the way is the record.

### Due dates and the week view: `getDueInfo(habit)` / `getWeekData(habit)`

`getDueInfo` answers "is this habit due today, and has it already gone
overdue" — it's what drives the "due today" badge on the card and the
reminder buzzer (see below). `getWeekData` builds the last 7 days and
classifies each one as `hit` (done), `due` (today, not done yet), `missed`
(a past due date that passed with nothing logged — the day that actually
broke the streak), or `neutral` (a free skip day inside the interval, no
action needed). Today's status is pulled from `getDueInfo` rather than
recomputed separately, so the week dot for today can never disagree with the
badge on the card above it.

## Reflecting on a broken streak

The streak mechanic is built on loss aversion — losing it is supposed to
sting a little. So instead of a broken streak just silently resetting to 0,
the next time you go to check that habit back off, a prompt interrupts the
tap and shows how far you'd gotten. If you'd set a `reason` up front (the
"Why does this matter to you?" field in the add/edit sheet), it's quoted
back at you verbatim, and you have to *retype it, word for word*, before
"I confirm that I commit myself again to my habit. I am accountable to
myself" becomes clickable — the whole point is making you write your own
words again, not just tap through a dialog. The match is case-insensitive
but otherwise exact. If there was no `reason` on file yet, any non-empty
answer counts and gets saved as the habit's reason going forward. Either
way, "Not now" just closes the prompt and leaves the habit untouched — it'll
ask again next time, since nothing was acknowledged.

This is gated by `getDueInfo(habit).isOverdue` plus a habit having actually
had `completedDates` before (a brand-new habit that's simply never been
started isn't a "failure," so it's never prompted). `lastAcknowledgedFailure`
stores *which* missed due date you've already reflected on, so the prompt
fires exactly once per broken streak rather than every single tap.

## Reminders (the "buzzer")

When a habit becomes due today, the app fires off a buzz: an in-app banner,
a short two-tone beep (via the Web Audio API, no audio file needed), and a
vibration on phones that support it. This runs automatically whenever the
app is open — on load, whenever you switch back to the tab, and every 5
minutes while it stays open — but it only ever buzzes **once per habit per
day** (tracked in `localStorage` under `streaks.notifiedToday.v1`); the
5-minute recheck just catches a due date arriving while the app happens to
be sitting open, it's not a repeating nag.

Each habit also has its own mute switch — the bell icon in its action row
(next to edit/delete) toggles `remindersEnabled`. Muting a habit skips the
beep/vibration/OS notification entirely, but doesn't hide the passive visual
cue: the "due today" badge and the amber pulsing week-dot are computed
straight from `getDueInfo`/`getWeekData` regardless of mute state, so a
muted low-stakes habit (there's rarely a real emergency around "eat chicken")
still visibly flickers when it's due — you just won't get buzzed about it.

Tapping the bell icon in the header additionally requests permission for a
real OS notification (the kind with an icon in your notification tray) via
the browser's `Notification` API, on top of the in-app buzz.

**The honest limitation**: none of this can wake your phone if the app
isn't running. There's no backend here to push a notification to a closed
browser — that would need a real push server (Web Push), which is a
meaningfully bigger project (hosting, a subscription database, a scheduler).
What you get instead is a fairly good approximation: the moment you open the
app on the due day, you get buzzed immediately, and it'll keep re-checking
every few minutes for as long as you leave it open.

Platform notes:
- **Android**: the `Notification` API works in a normal browser tab, no
  install required.
- **iPhone**: Safari only allows web notifications for a page that's been
  "Added to Home Screen" first (which is why this app has a
  [manifest.json](manifest.json) and [sw.js](sw.js) — those are what make
  that install option show up). Even installed, it's still the same
  limitation: no wake-from-closed, just an immediate buzz on open.

## Cosmetic theme packs

`THEME_PACKS` (top of the script) lists the free "Ember" gradient plus a
few paid re-skins (Blue flame, Neon pulse, Emerald ember) — each is just an
alternate pair of colors for the same `--ember-1`/`--ember-2` CSS variables,
applied via a `[data-pack="..."]` attribute on `<html>` (see `styles.css`).
No new logic per pack, just different numbers.

The shop itself (`ThemeModal`) is opened from a 🎨 button that's always in
the header — every pack is purchasable from day one, not gated behind any
streak. A small red dot on that icon (`cosmetics.shopViewed`, false until
the shop's been opened once) is the actual discovery nudge — cheap,
un-pushy, clears itself the first time anyone taps in, regardless of
whether they buy anything. Separately, the first time any habit's current
streak reaches `THEME_UNLOCK_STREAK` (10 days), a one-time celebratory
banner points at the shop as a "nice work, go treat yourself" moment —
not an unlock, since nothing was ever hidden. `cosmetics.unlocked` just
tracks whether that banner has already fired, so it doesn't repeat on
every check-in after the first.

Owning/activating a paid pack also recolors and animates the flame logo
next to the app name in the header — the free Ember pack leaves it as the
plain static 🔥 emoji, untouched. It's still the *same* emoji, not custom
artwork: emoji glyphs are fixed-color bitmaps that `color` can't touch,
but CSS `filter` operates on the rendered pixels regardless of source, so
`hue-rotate()` (see `.app-title .flame.pack-*` in `styles.css`) shifts an
otherwise-unrecognizable-at-this-size custom icon problem into "same
legible shape, different color" instead. A separate inner span layers a
looping scale/rotate animation on top for the flicker effect.

"Buying" a pack right now only sets `activePack`/`purchased` locally —
there's no real payment processor wired in yet, which the modal's footer
note is upfront about. That'll need to be swapped for actual App
Store/Play Store billing once this is wrapped in something like Capacitor
for real distribution.

## Design notes

- **Colors**: a warm cream/charcoal base with an orange→gold "ember"
  gradient used *only* for streak numbers and a habit's lit-up state, so it
  reads as something earned rather than decoration.
- **Fonts**: Baloo 2 (chunky, rounded) for the streak numbers and headings,
  Inter for body text.
- **Signature interaction**: tapping a habit's icon "ignites" it — a quick
  scale/rotate pop plus a bump on the streak number — and hitting a 7/30/100
  day milestone triggers a brief confetti burst.
- **Mobile-first**: single column, capped at 480px wide, 44px+ tap targets,
  and the primary "add" action is a thumb-reachable floating button pinned
  near the bottom of the screen.

## Native app wrapping

The web app (root `index.html` + friends) is still the actual source of
truth — nothing about how you edit or test it in a browser has changed.
[Capacitor](https://capacitorjs.com) just wraps a *copy* of those files in
a real native shell so the result can be submitted to the App Store and
Play Store, since neither accepts a bare web link.

Capacitor requires its web assets to live in their own dedicated folder
(`webDir`) rather than the project root — Capacitor's own tooling refuses
to treat the whole project root as that folder (it would otherwise try to
copy `node_modules/`, `android/`, `ios/`, etc. into the native app). `www/`
is that folder: a plain copy of the six real app files, nothing more.

**This means editing `index.html` or `styles.css` in the root no longer
automatically reaches the native apps.** Run:

```
npm run sync
```

after any change, before building/testing natively. This copies the root
files into `www/` and then runs `npx cap sync`, which copies `www/` into
both `android/app/src/main/assets/public/` and `ios/App/App/public/` and
updates native plugin config. Skipping this step means the native apps
keep running whatever was last synced, silently out of date.

`android/` and `ios/` are Capacitor-generated native projects — don't hand-edit
files inside them expecting changes to persist; they get overwritten by
`cap sync`. Building Android works locally on Windows via Android Studio.
Building iOS needs Xcode, which only runs on macOS — see the "GitHub
Actions + Fastlane" plan discussed for building/signing iOS without owning
a Mac.

## Extending it

A few natural next steps, roughly in order of effort:

- **Real background push notifications** — the thing the in-app buzzer
  can't do: wake your phone when the app is fully closed. Needs a small
  backend (store each device's push subscription, a scheduler to trigger
  sends at the right local time) and, for iPhone, the app installed to the
  home screen first. Biggest jump in complexity on this list.
- **Streak freeze** — let a habit survive one missed day. You'd add a
  `freezesUsed` field per habit and adjust `getCurrentStreak` to tolerate a
  single gap.
- **Editing past days** — right now you can only check off *today*. Tapping
  a day in `WeekDots` to toggle it would need a small change to
  `handleToggleToday` to accept a date key instead of always using
  `todayKey()`.
- **Splitting into real files** — once you're ready to introduce a build
  tool (Vite is the easiest for a React project like this), you can lift
  sections 1–7 out of `index.html` into their own files
  (`utils/streaks.js`, `components/HabitCard.jsx`, etc.) almost as-is —
  the logic doesn't depend on the single-file setup, only the *loading
  mechanism* does.
